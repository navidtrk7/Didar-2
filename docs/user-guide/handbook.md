## ۰. شروع سریع پایلوت

حداقل مسیر برای اثبات محصول (یک دور کامل):

| # | نقش پیشنهادی | کار | مسیر |
|---|---------------|-----|------|
| ۱ | تولیدکننده (`arash`) | تعریف SKU و ارسال به QC | `/app/product/catalog` |
| ۲ | QC (`maryam`) | تأیید وزن و پاس کردن | `/app/product/qc` |
| ۳ | انبار (`hossein`) | در صورت نیاز صدور/تأیید UID | `/app/inventory/uids` |
| ۴الف | ایجنت (`navid`) | قفل قیمت + پیش‌فاکتور | `/app/commerce/proforma` |
| ۴ب | خرده‌فروش (`sara`) | سفارش از کاتالوگ (با UID) | `/app/retailer/catalog` |
| ۵ | انبار | صف تحقق: برداشت → بسته‌بندی → تحویل | `/app/fulfillment` |
| ۶ | مالی (`kambiz`) | تسویه تولیدکننده → ثبت در آداپتر زرین (تست) | `/app/finance/settlements` |
| ۷ | انبار | اختلاف فیزیکی در صورت نیاز | `/app/inventory/custody` |

اگر حساب چندنقشی است (مثلاً `navid` = ایجنت + انبار)، از سایدبار **نقش فعال** را عوض کنید — منو عوض می‌شود.

## ۱. دیدار چیست

پلتفرم **عملیاتی** برای زنجیرهٔ طلا:

```
کارخانه / آتلیه → QC → خزانه (UID) → قیمت → پیش‌فاکتور / سفارش
→ برداشت / بسته‌بندی / تحویل (کد تأیید) → اعتبار / دفتر → گارانتی
```

طرف‌های بازار ایران در «شبکه» مدل می‌شوند: کارخانه، کارگاه، بنکدار، گالری، خزانه، میز ایجنت، مشتری سازمانی، واحد داخلی.

## ۲. نوار کناری و حساب فعال

- منو بر اساس **نقش فعال** ساخته می‌شود (پیش‌فرض = نقش اصلی؛ اگر نقش اضافه دارید قابل تعویض است).
- اگر بیش از یک نقش دارید، در سایدبار **نقش فعال (کلاه کاری)** را ببینید و عوض کنید.
- اگر کاربر به چند طرف (فروشگاه/کارخانه/…) وصل باشد، **محل کار فعال** هم در سایدبار ظاهر می‌شود.
- **تعویض حساب** → برگشت به صفحهٔ ورود.
- **خروج از حساب** → پایان جلسه.

## ۳. مفاهیم کلیدی

این سه مفهوم را قاطی نکنید:

### ۳.۱ طرف شبکه (Party / Organization)
**موجودیت بازار** — نه لزوماً یک انسان.

مثال‌ها: گالری مهر طلا، بنکدار پارسا، آتلیه نوا، خزانه تهران.

- می‌تواند **بدون مسئول** باشد (فروشگاه تازه‌تأسیس قبل از معرفی نماینده).
- پروفایل دارد: چه می‌کند، قابلیت‌ها، شهر، تلفن، جواز، …
- مسیر: `/app/network` → تب «طرف‌ها / فروشگاه‌ها»

### ۳.۲ شخص / کاربر (User)
انسان واردشونده به سیستم.

- یک **نقش اصلی** دارد.
- می‌تواند **نقش‌های اضافه** بگیرد (چندنقشی).
- می‌تواند عضو **چند طرف** باشد (چندمحل).

### ۳.۳ نقش (Role) در برابر نوع طرف (Party kind)

| | نقش (Role) | نوع طرف (Kind) |
|--|------------|----------------|
| معنی | چه ابزارهایی در اپ می‌بیند / چه مجوزی دارد | این موجودیت در بازار طلا چیست |
| مثال | `producer`، `agent`، `warehouse` | کارخانه، بنکدار، گالری |
| کجا | کاربران / اعطای نقش | شبکه → افزودن طرف |

**مثال:** یک ایجنت می‌تواند همزمان عضو «میز ایجنت» و یک بنکدار باشد و نقش اضافهٔ انبار هم داشته باشد.

### ۳.۴ SKU در برابر UID
| SKU | UID |
|-----|-----|
| تعریف محصول کاتالوگ (مدل، عیار، وزن کاتالوگ) | شناسهٔ یکتای قطعهٔ فیزیکی مهرشده |
| قبل از تأیید QC ممکن است پیش‌نویس باشد | بعد از تأیید QC و صدور انبار |
| چند قطعه می‌توانند از یک SKU باشند | هر قطعه یک UID |

### ۳.۵ موقعیت انبار در برابر طرف شبکه
- **طرف شبکه:** گالری / کارخانه به‌عنوان شاوک کسب‌وکار.
- **موقعیت موجودی (Inventory location):** خزانه تهران-الف، قفسه، … برای موجودی فیزیکی.

وصل کردن کاربر به «گالری» ≠ تخصیص موقعیت انبار. این دو لایه جدا هستند.

### ۳.۶ قفل قیمت و پیش‌فاکتور
چون نرخ طلا لحظه‌ای است:
1. قفل قیمت برای چند دقیقه (تنظیمات سیستم).
2. افزودن UIDها به پیش‌فاکتور.
3. صدور پیش‌فاکتور با کنترل اعتبار خرده‌فروش.

## ۵. راه‌اندازی شبکه: طرف‌ها، افراد، محل‌ها

مسیر اصلی: **`/app/network`** (نیاز به API فعال).

| نقش | دسترسی |
|-----|--------|
| ادمین | مشاهده + مدیریت کامل (ساخت طرف، تخصیص، نقش، بایگانی) |
| ایجنت / مالی | مشاهده شبکه (فروش و اعتبار) — بدون مدیریت |
| تولیدکننده / خرده‌فروش / QC / انبار / مشتری / قیمت‌گذاری | بدون منوی شبکه |

### ۵.۰ مدل پروفایل (ذهنیت دیدار)

هر طرف شبکه یک Profile است — نه لزوماً یک User.

| مرحله | معنی |
|-------|------|
| اجباری اولیه | حداقل برای ثبت موجودیت |
| فعال‌سازی | قبل از عملیات واقعی (مثلاً حداقل یک عضو) |
| اختصاصی دیدار | `trust_tier`، منطقه، ایجنت، مرجع زرین |
| بلوغ / سیستم‌ساخته | KPI و شرایط پیچیده — **فرم ثبت‌نام نیست** |

طرف ≠ کاربر. ایجنت با **تخصیص** وصل می‌شود. در پروفایل طرف، ستون «آمادگی» همین ذهنیت را نشان می‌دهد.

### ۵.۱ افزودن طرف (فروشگاه، کارخانه، بنکدار، …)
1. تب **طرف‌ها / فروشگاه‌ها**.
2. **افزودن طرف شبکه**.
3. نوع را انتخاب کنید:

| نوع | کاربرد کوتاه |
|-----|---------------|
| کارخانه | تولید عمده |
| کارگاه / آتلیه | ساخت سفارشی و محدود |
| بنکدار | واسطه عمده |
| گالری / فروشگاه | خرده‌فروشی |
| خزانه / انبار | نگهداری و pack/handover |
| میز ایجنت | فروش میدانی و پیش‌فاکتور |
| مشتری سازمانی | حساب خدمات پس از فروش |
| واحد داخلی | ستاد، QC، مالی، … |

4. مشخصات پروفایل (شهر، تلفن، جواز، …) را پر کنید.
5. مسئول **الزامی نیست** — اول موجودیت، بعد شخص.

### ۵.۲ باز کردن پروفایل طرف
در جدول طرف‌ها روی **نام** کلیک کنید. پنل «پروفایل طرف» باز می‌شود:

- این طرف چه می‌کند؟
- قابلیت‌ها
- تماس / آدرس / جواز
- اعضا
- دکمه‌ها: **تخصیص شخص**، **بایگانی**

### ۵.۳ تخصیص شخص به طرف (محل)
1. پروفایل طرف را باز کنید.
2. **تخصیص شخص**.
3. کاربر + عنوان (مثلاً «خریدار گالری») را بزنید.

یک نفر می‌تواند به چند طرف وصل شود → در سایدبار چند **حساب فعال** می‌بیند.

### ۵.۴ اشخاص و نقش‌ها در شبکه
- تب **اشخاص:** فهرست افراد + نقش اصلی + همه نقش‌ها + سازمان اصلی.
- تب **نقش‌ها:** نقش‌های سیستمی و سفارشی؛ نقش سفارشی قابل تعریف و بایگانی است.
- **اعطای نقش** (از تب اشخاص): نقش اضافه به شخص.

## ۶. کاربران، ویرایش، چندنقشی

مسیر: **`/app/admin/users`** (حاکمیت — معمولاً ادمین).

### ۶.۱ دعوت کاربر جدید
1. **دعوت کاربر**
2. نام، نام کاربری، ایمیل، **نقش اصلی**، **سازمان / محل اصلی**
3. وضعیت اولیه: **دعوت‌شده** → با دکمهٔ **فعال** فعال کنید.

### ۶.۲ ویرایش کاربر
دکمهٔ **ویرایش**:

- نام / نام کاربری / ایمیل
- نقش اصلی
- سازمان اصلی
- نقش‌های اضافه (حذف از همین مودال)

### ۶.۳ افزودن چند نقش به یک نفر
مثال: بنکدار + تولیدکننده + تحویل‌گیر

1. طرف‌های لازم را در شبکه بسازید (بنکدار، کارخانه/آتلیه، میز ایجنت یا خزانه).
2. کاربر را دعوت/ویرایش کنید؛ **نقش اصلی** را پراستفاده‌ترین نقش روزمره بگذارید (مثلاً `agent`).
3. کاربر را به همهٔ طرف‌های مرتبط **تخصیص** دهید.
4. با **نقش اضافه** نقش‌های `producer`، `warehouse` و … را بدهید.

یا از **شبکه → اشخاص → اعطای نقش**.

### ۶.۴ چندنقشی در عمل
- **نقش اصلی** روی حساب کاربر ثبت است.
- **نقش‌های اضافه** هم ثبت می‌شوند؛ API مجوزها را به‌صورت اتحاد نقش‌ها اعمال می‌کند.
- برای کار روزمره، در سایدبار **نقش فعال** را روی همان کلاهی بگذارید که الان می‌خواهید کار کنید — منو عوض می‌شود.
- **چند محل** با عضویت در طرف‌ها و تعویض **محل کار فعال** مدیریت می‌شود.

## ۸. جریان سرتاسری طلا

جریان طلایی از تولید تا مشتری:

```text
[۱ تولید/کاتالوگ] تعریف SKU
        ↓
[۲ QC] اندازه‌گیری وزن / تأیید یا اصلاح
        ↓
[۳ انبار] صدور UID مهرشده + موجودی خزانه + دفتر
        ↓
[۴ قیمت] نرخ زنده / قوانین اجرت / قفل قیمت
        ↓
[۵ فروش] پیش‌فاکتور ایجنت یا سفارش خرده‌فروش
        ↓
[۶ تحقق] برداشت → بسته‌بندی → تحویل به ایجنت → کد تأیید (فعلاً دمو)
        ↓
[۷ مالی] اعتبار / مطالبات / تسویه (آداپتر زرین — حالت تست تا کلید واقعی)
        ↓
[۸ خدمات] گارانتی (فقط پس از تحویل) / استعلام اصالت با UID
```

هر مرحله می‌تواند نقش متفاوتی داشته باشد؛ یک نفر چندنقشی با تعویض **نقش فعال** چند مرحله را پوشش می‌دهد.

## ۹. جریان‌های جزئی به تفکیک دامنه

### ۹.۱ محصول و QC — `/app/product`

**هدف:** تعریف مدل و تأیید کیفیت قبل از ورود به خزانه.

| مرحله | صفحه | کار |
|-------|------|-----|
| تعریف | `/app/product/catalog` | افزودن SKU + تصویر (پیش‌نویس یا ارسال مستقیم به QC) |
| صف | `/app/product` یا `/app/product/qc` | دیدن منتظرها |
| بازرسی | `/app/product/qc` | وزن اندازه‌گیری، قبول / رد / اصلاح |
| کالکشن | `/app/product/collections` | گروه‌بندی ویترینی |

پس از **تأیید QC**، سامانه معمولاً خودش UID را صادر می‌کند؛ صفحهٔ انبار برای تأیید/صدور مجدد هم امن است (idempotent).

برای ارسال مستقیم به صف QC، هنگام ثبت SKU گزینهٔ ارسال به QC را فعال کنید.

### ۹.۲ موجودی و UID — `/app/inventory`

| مرحله | صفحه | کار |
|-------|------|-----|
| صدور | `/app/inventory/uids` | برای SKU تأییدشده UID صادر کنید |
| موجودی | `/app/inventory/stock` | وزن/تعداد بر اساس موقعیت |
| تخصیص | `/app/inventory/allocation` | رزرو برای سفارش/پیش‌فاکتور |
| حضانت | `/app/inventory/custody` | انتقال مسئولیت فیزیکی + ثبت اختلاف وزن |

در اختلاف فیزیکی، UID قفل می‌شود تا پرونده بسته شود (تأیید وزن پلمپ یا پذیرش وزن جدید).

پس از مهر شدن، قطعه در استعلام عمومی `/verify/[uid]` قابل پیگیری است.

### ۹.۳ تجارت و قیمت — `/app/commerce`

| کار | صفحه |
|-----|------|
| نمای کلی تجارت | `/app/commerce` |
| قیمت‌گذاری (نرخ زنده) | `/app/commerce/pricing` |
| شبیه‌ساز / قوانین / درخواست نرخ | پارک |
| قوانین اجرت | `/app/commerce/pricing/rules` |
| درخواست تغییر نرخ | `/app/commerce/pricing/rate-requests` |
| پیش‌فاکتور ایجنت | `/app/commerce/proforma` |
| گالری سیار | `/app/commerce/gallery` |
| سفارش‌ها | `/app/commerce/orders` |
| کاتالوگ خرده‌فروش | `/app/retailer/catalog` |
| اعتبار خرده‌فروش | `/app/retailer/credit` |

پروموشن فعلاً پارک است (تا موتور اعمال قیمت آماده شود).

#### جریان پیش‌فاکتور (ایجنت)
1. خریدار (خرده‌فروش دارای حساب اعتبار) را انتخاب کنید.
2. UID را وارد کنید (خالی = اولین موجود؛ اشتباه = خطا، نه افزودن تصادفی).
3. قفل قیمت فعال می‌شود (مدت از تنظیمات سیستم).
4. **صدور پیش‌فاکتور** — اگر اعتبار مسدود/ناکافی باشد، صدور متوقف می‌شود.

#### جریان سفارش خرده‌فروش
1. `/app/retailer/catalog` → ثبت سفارش روی قطعه (با UID).
2. سفارش به سازمان خود خرده‌فروش می‌چسبد؛ اعتبار همان سازمان چک می‌شود.
3. تخصیص + صف تحقق به‌صورت اتمیک شروع می‌شود → `/app/commerce/orders` و `/app/fulfillment`.

### ۹.۴ تحقق سفارش — `/app/fulfillment`

| مرحله | صفحه | دکمهٔ نوعی |
|-------|------|------------|

`scheduled → picking → packing → handover → en_route / awaiting_otp → completed`

**OTP:** فعلاً کد دمو است (SMS واقعی هنوز وصل نیست). در پایلوت برای عبور از مرحله کافی است.

## ۱۰. راهنمای هر نقش

**اصل دسترسی:** اگر نقشی مجوز ندارد، ابزار در منو و میانبرها **پنهان** است؛ ورود مستقیم به URL هم به خانهٔ نقش برمی‌گردد (بدون پیام خطای بن‌بست).

| نقش | منوی اصلی (خلاصه) | ندارد |
|-----|-------------------|--------|
| admin | همه دامنه‌ها + حاکمیت | — |
| qc | محصول / کاتالوگ / QC | شبکه، انبار، تجارت، مالی |
| producer | محصول / کاتالوگ | QC تأیید، شبکه، انبار |
| warehouse | موجودی (UID/تخصیص/حضانت/اختلاف) + تحقق مراحل | شبکه، قیمت، مالی |
| pricing | تجارت قیمت + کاتالوگ | سفارش، شبکه، انبار عملیاتی |
| agent | تجارت، شبکه، موجودی/حضانت، تحویل نهایی، گارانتی، تسویه اعتماد | صدور UID (مگر نقش اضافه انبار)، قیمت‌گذاری عمیق، CRM |
| retailer | تجارت/سفارش، موجودی شعبه، اعتبار شعبه، مرجوعی/بازخرید | شبکهٔ کامل، خزانه، مالی ستاد |
| finance | مالی، موجودی خواندنی، شبکه، خدمات پس از فروش | صدور UID، پیش‌فاکتور، QC، هوش (پارک) |
| customer | گارانتی + استعلام اصالت | بازخرید/مرجوعی عملیاتی، شبکه |

### مدیر کل (`admin`)
- راه‌اندازی شبکه و کاربران
- نظارت ممیزی و تنظیمات
- دسترسی گسترده به دامنه‌ها
- مسیر شروع: `/app/admin`

### QC / کاتالوگ (`qc`)
- ساخت و ارسال SKU به QC
- بازرسی وزن و نتیجه
- مسیر: `/app/product` ، `/app/product/qc` ، `/app/product/catalog`

### تولیدکننده (`producer`)
- تعریف محصول و طرح از دامنهٔ محصول
- ارسال به صف QC — صفحهٔ بازرسی/تأیید را نمی‌بیند (فقط نقش QC/ادمین)
- معمولاً به طرف «آتلیه/کارخانه» وصل است
- مسیر: `/app/product`

### انبار (`warehouse`)
- صدور UID
- موجودی، تخصیص، حضانت
- مراحل تحقق (برداشت/بسته‌بندی/handover)
- مسیر: `/app/inventory` ، `/app/fulfillment`

### قیمت‌گذاری (`pricing`)
- نرخ سامانه + قفل قیمت روی پیش‌فاکتور (عمق قوانین/شبیه‌ساز پارک)
- مسیر: `/app/commerce/pricing/...`

### ایجنت (`agent`)
- پیش‌فاکتور، گالری سیار، سفارش‌ها، مشاهده شبکه
- حضانت و تحویل نهایی / کد تأیید دمو (1234)
- گارانتی (ارتباطات/CRM پارک)
- تعویض حساب فعال اگر چند محل دارد
- مسیر: `/app/commerce` ، `/app/fulfillment/delivery`

### خرده‌فروش (`retailer`)
- کاتالوگ، ثبت سفارش، اعتبار و موجودی **شعبه** (نه خزانهٔ کل)
- مرجوعی / بازخرید در خدمات
- مسیر: `/app/commerce` ، `/app/retailer/catalog`

### مالی (`finance`)
- دفتر، اعتبار، تسویه، تعدیل
- مشاهده شبکه و موجودی (خواندنی) + چرخه خدمات پس از فروش
- مسیر: `/app/finance`

### مشتری (`customer`)
- گارانتی و استعلام اصالت — بدون منوی بازخرید/مرجوعی عملیاتی
- مسیر: `/app/service/warranty` ، `/verify`

## ۱۳. چک‌لیست راه‌اندازی

1. [ ] طرف‌های واقعی در شبکه تعریف شوند.
2. [ ] کاربران دعوت و فعال شوند؛ نقش اصلی درست باشد.
3. [ ] هر کاربر به طرف(های) درست تخصیص داده شود.
4. [ ] نقش‌های اضافه برای افراد چندکاره ثبت شود.
5. [ ] تنظیمات: تلورانس وزن QC، مدت قفل قیمت، منبع نرخ.
6. [ ] یک جریان کامل تست شود: SKU → QC → UID → پیش‌فاکتور/سفارش → تحقق (بخش ۰).
7. [ ] اعتبار خرده‌فروشان و سقف‌ها وارد شود.
8. [ ] سیاست بایگانی طرف/نقش مشخص شود.
9. [ ] قبل از دادهٔ واقعی مشتری: `DEMO_SEED=false`، چرخش JWT، بکاپ Postgres.

## پیوست ب — الگوی «یک نفر چند کسب‌وکار»

**سناریو:** علی هم بنکدار است، هم تولید محدود دارد، هم گاهی تحویل می‌گیرد.

| لایه | اقدام |
|------|--------|
| طرف‌ها | بنکدار + آتلیه + (اختیاری) میز ایجنت |
| عضویت | علی را به هر سه وصل کنید |
| نقش اصلی | پرکاربردترین نقش روزمره (مثلاً `agent` یا `producer`) |
| نقش اضافه | نقش‌های دیگر برای ثبت چندنقشی |
| کار روزانه | **نقش فعال** را برای ابزار عوض کنید؛ **محل کار فعال** را برای طرف عوض کنید |
